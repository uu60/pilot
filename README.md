# PILOT

**PILOT** stands for **Parallel In-path Lane-Oriented Triples**. It is a compact prototype derived from **Parsec** for evaluating a switch-assisted BMT delivery architecture for Boolean MPC.

PILOT is not intended to replace the full Parsec framework. Instead, it keeps the Parsec-style module organization and operator calling convention while removing features that are not needed for this experiment. The current focus is Boolean batch MPC, fixed-lane parallel execution, in-path BMT payload delivery, and a simplified secure database sort workflow.

## Background

In the original Parsec design, BMTs are treated as preprocessing material managed by the MPC runtime. PILOT explores a different architecture: BMTs are generated by a switch-like component on the communication path and appended to normal server-to-server messages.

The original software baseline uses four MPI ranks:

- `rank 0`: MPC server 0
- `rank 1`: MPC server 1
- `rank 2`: client and data holder
- `rank 3`: simulated switch

Newer routed modes separate process launch from communication. The pilot servers still send to the peer server, while a switch-like component in the network path decides whether the packet is a normal message or a BMT-bearing `e/f` exchange. During the Boolean AND `e/f` exchange, the switch forwards the original payload and appends a fixed-size BMT bundle for future AND operations. This makes BMT delivery passive and avoids adding extra BMT communication rounds.

## Architecture

PILOT uses fixed-lane parallelism. The maximum parallelism is configured at system initialization, and the number of BMT lanes is set to the same value. Each lane has one worker thread and one independent BMT stream.

Operators should be executed through the lane thread pool:

```cpp
auto future = LaneThreadPool::submit(laneId, [&] {
    BitwiseEqualOperator op(&xShares, &yShares, width,
                            SecureOperator::NO_CLIENT_COMPUTE);
    return op.execute()->_zis;
});
```

Within one lane, operators execute sequentially. Across lanes, operators execute in parallel. This avoids BMT ordering conflicts because each lane consumes only its own BMT stream.

## BMT Model

Only `BitwiseAndOperator` directly consumes BMTs. Higher-level operators such as Equal, Less, and Mutex are built from AND and do not manage BMTs themselves.

PILOT intentionally uses a simple width model:

- Supported bit width: `1..64`
- Each logical AND input consumes one 64-bit raw BMT
- If `width < 64`, only the low `width` bits are used
- The remaining bits are wasted by design

This avoids complex packed-BMT accounting and makes bundle usage deterministic.

## Build

PILOT uses CMake and MPI.

```bash
cd pilot
cmake -S . -B build
cmake --build build -j
```

## Transport Programming Model

PILOT has two communication implementations behind the `Comm` interface:

- `MpiComm`: the original four-rank MPI software switch baseline.
- `RoutedComm`: the newer communication path used for standalone software switch, TAP switch simulation, and BMv2 experiments.

`RoutedComm` sends `RoutedPeerMessage` objects through a `RoutedPeerTransport` backend. The transport backend owns only the byte/frame transport mechanism; it should not contain MPC or BMT semantics.

Current transport roles:

- `TcpSoftwareSwitchTransport`: software baseline transport. All routed messages go through one TCP software switch process. The switch forwards ordinary messages and only appends BMT when it sees a server-to-server Pilot switch request.
- `TapRoutedPeerTransport`: Linux `AF_PACKET`/raw Ethernet transport. Pilot ranks bind TAP/veth interfaces and send Ethernet frames to the peer rank. The external switch process is selected by the network topology, not by pilot code.
- `TapFrameCodec`: Ethernet wrapper for `PilotWireMessageCodec`.
- `PilotWireMessageCodec`: shared Pilot wire header used by TCP software switch, TAP switch, and BMv2/P4.

The intended programming rule is:

```text
pilot endpoint code sends to the peer rank
transport code serializes and transmits the message
switch code decides whether to append BMT
pilot endpoint code must not explicitly request BMT from a switch
```

This keeps the software switch, C++ TAP switch, BMv2, and future FPGA direction aligned: the switch is in the path, while the two compute parties treat communication as peer-to-peer.

## Run Modes

### MPI Software Baseline

The original MPI mode requires four MPI processes because the switch is modeled as an additional MPI rank.

```bash
mpirun -np 4 build/db/benchmark/pilot_db_sort \
  --rows=16 \
  --in_path_max_parallelism=4 \
  --in_path_bmt_bundle_size=64
```

### Routed TCP Software Switch

This mode does not use MPI for process orchestration. The launcher starts `switch`, `server0`, `server1`, and `client`. All routed messages go through `TcpSoftwareSwitchTransport`.

```bash
build/launcher/pilot_routed_launcher \
  --program=build/db/benchmark/pilot_db_sort \
  --rows=8 \
  --simulation_level=software \
  --routed_network=tcp \
  --in_path_max_parallelism=2 \
  --in_path_bmt_bundle_size=16 \
  --tcp_switch_port=19000
```

### Routed TAP with C++ Switch Simulator

This mode starts the switch outside pilot. Pilot ranks only bind TAP/veth endpoint interfaces and send to peer ranks.

Example topology:

```text
server0: tap0 <-> tap-sw0 : switch
server1: tap1 <-> tap-sw1 : switch
client : tap2 <-> tap-sw2 : switch
```

Start the C++ switch:

```bash
build/switch_simulator/pilot_tap_switch \
  --tap_server0=tap-sw0 \
  --tap_server1=tap-sw1 \
  --tap_client=tap-sw2
```

Run pilot endpoints:

```bash
build/launcher/pilot_routed_launcher \
  --program=build/db/benchmark/pilot_db_sort \
  --rows=8 \
  --simulation_level=simulator \
  --routed_network=tap \
  --routed_tap_server0=tap0 \
  --routed_tap_server1=tap1 \
  --routed_tap_client=tap2 \
  --in_path_max_parallelism=2 \
  --in_path_bmt_bundle_size=16
```

The C++ TAP switch is the current full reference for external transparent switch behavior. It calls `InPathSwitchSimulator::forwardRequest()` and appends simulated BMT shares.

### Routed TAP with BMv2/P4

BMv2 is started outside pilot and binds the same switch-side veth interfaces. Pilot endpoint arguments are the same as the C++ TAP switch mode.

Compile and start BMv2:

```bash
p4c --target bmv2 --arch v1model p4/pilot_wire.p4 -o build-p4

simple_switch \
  -i 0@tap-sw0 \
  -i 1@tap-sw1 \
  -i 2@tap-sw2 \
  build-p4/pilot_wire.json
```

Install forwarding and current functional BMT table entries:

```bash
simple_switch_CLI < p4/rank_forwarding.cli
simple_switch_CLI < p4/bmt_zero.cli
```

Then run pilot endpoints with the same TAP command shown above.

Current BMv2 status:

- It parses the Pilot wire header and forwards by `receiver_rank`.
- It can rewrite bounded switch requests into envelopes for `payload_size in {1,2,4,8,16,32}` and `bmt_count in {4,16}`.
- Its current BMT source is all-zero functional validation data, not secure BMT material.
- The C++ TAP switch remains the reference for real simulated BMT generation.

### Runtime Options

Important runtime options:

- `--in_path_max_parallelism=N`: number of fixed lanes and worker threads
- `--in_path_bmt_bundle_size=N`: fixed BMT bundle size per lane
- `--in_path_switch_rank=N`: switch rank, default is `3`
- `--comm=mpi|routed`: communication implementation, normally supplied by `mpirun` or the routed launcher
- `--simulation_level=software|simulator`: built-in software switch or external in-path simulator
- `--routed_network=tcp|tap`: TCP software switch backend or TAP/raw Ethernet backend
- `--routed_tap_server0=IFACE`, `--routed_tap_server1=IFACE`, `--routed_tap_client=IFACE`: pilot-side TAP/veth interfaces

## Operator Usage

If the client holds plaintext inputs, use `Comm::CLIENT_RANK`:

```cpp
std::vector<int64_t> xs{1, 2, 3};
std::vector<int64_t> ys{1, 5, 3};
int width = 4;

BitwiseEqualOperator eq(&xs, &ys, width, Comm::CLIENT_RANK);
eq.execute()->reconstruct(Comm::CLIENT_RANK);

if (Comm::isClient()) {
    for (auto v : eq._results) {
        std::cout << v << " ";
    }
}
```

If the servers already hold secret shares, use `SecureOperator::NO_CLIENT_COMPUTE`:

```cpp
BitwiseAndOperator op(&xShares, &yShares, width,
                      SecureOperator::NO_CLIENT_COMPUTE);
auto zShares = op.execute()->_zis;
```

When using in-path BMTs, run operators that require AND inside a lane worker. The application layer only needs to manage lane assignment and batch size. BMT request, delivery, storage, and consumption are handled internally by the runtime, communication layer, switch simulator, and `BitwiseAndOperator`.

## Current Scope and Limitations

- Only Boolean batch MPC operators are supported.
- The original MPI switch is a software baseline.
- The C++ TAP switch is the current full external simulator reference.
- The BMv2/P4 switch is a bounded functional prototype and currently uses fake all-zero BMT data.
- Parallelism is fixed at initialization time.
- Free-threaded operator execution is intentionally unsupported.
- Each lane is sequential; parallelism is across lanes.
- A single `BitwiseAndOperator` batch may not exceed the configured BMT bundle size.
- `BitwiseMutexOperator` consumes two AND streams, so its batch size should not exceed half of the BMT bundle size.
- Multi-column sort currently uses a packed comparison key and supports total key width up to 62 bits.

## Relationship to Parsec

PILOT inherits its coding style, module layout, and core MPC operator structure from Parsec. The main difference is that PILOT removes the general-purpose Parsec configuration space and specializes the runtime around the in-path BMT architecture. This makes it easier to reason about lane safety, BMT ordering, and switch-assisted delivery.
